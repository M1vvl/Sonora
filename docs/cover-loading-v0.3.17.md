# 0.3.17 封面加载复核

## 问题与处理

这次不是把全部图片改成“高优先级”。现有音乐页给首屏歌单和歌曲封面统一使用 `loading=lazy`，原图经常为1000px；小封面也会下载整张原图。后台音乐缓存只保留4项，六张或更多封面被重建时会反复逐出。番剧、影视某些图片服务器还会返回非标准 `image/jpg`，旧校验可能拒绝已收到的图片。

- `ui/cover-loading.js`：可见封面立即请求，邻近视口约220px提前准备，远处只保留 `data-cover-src`。首要封面单独高优先级，其余正常；异步解码后显示；可见失败最多补试一次。滚动/尺寸通知合并为单次帧，隐藏及销毁取消待办，不复制 Blob 或图片字节。
- 音乐：网易云原装 CDN `param=384y384` 实测返回缩略图，保留内容而减少传输；相同原图/缩略图地址合并；相同请求只下载一次，各消费者可独立取消，最后一个取消才取消底层下载。缓存64项/8MiB，上限仍为每图2MiB；网络仍最多4并发/64排队。服务端5xx或网络错误最多重试一次，整体有10秒期限。
- 番剧：优先采用条目API已提供的 `images.common`，缺少时保留原有large/medium回退；没有构造未知CDN地址或绕过用户的ECH设置。
- 番剧和影视：规范 `image/jpg` 为 `image/jpeg`；影视单次瞬时网络错误补试一次，沿用现有有界缓存、取消和来源校验。
- 页面原有固定尺寸和宽高属性继续占位；不会等待全部封面完成才显示文字或操作按钮。封面慢或不可用时不阻塞搜索、详情及播放。

## 调研依据

[web.dev 原生图片延迟加载](https://web.dev/articles/browser-level-image-lazy-loading)建议首屏关键图片直接加载、屏外图片延迟加载并保留尺寸；浏览器的延迟阈值并不等于“仅请求眼前一张”。因此横向卡片的较远内容使用明确的受控延后地址，避免同一屏附近过多封面抢占队列。

[web.dev Fetch Priority](https://web.dev/articles/fetch-priority)解释高优先级是相对提示，不能让所有图片同时获得更多带宽。本实现只提升首要封面，并保持并发上限。

[MDN 图片解码](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decoding)说明 `decoding=async` 本身不保证无空白；动态替换应结合真实解码状态。共享组件在收到真实加载后执行 `decode()`，同时保留失败回退。

## 实测与边界

`scripts/check-covers.cjs` 在独立用户目录、隐藏Chromium和匿名官方接口中执行，未读正式账号或桌面。报告 `artifacts/v0.3.17-covers/covers-report.json`；实际首屏截图 `covers-first-screen.png`。

2026-10-30，同一组六张真实歌单封面：

| 实现 | 首轮请求/字节/总耗时 | 再次读取请求/字节/耗时 |
| --- | --- | --- |
| 已安装0.3.16原图与4项缓存 | 6 / 450685B / 279ms | 6 / 450685B / 41ms |
| 当前384px缩略图与有界缓存 | 6 / 127359B / 622ms | 0 / 0B / 0ms |

该样本传输字节减少，但冷请求总耗时没有更快，不能把缩略图方案宣传为网络一定提速；请求延迟及首次CDN缩放会变化。复用时避免了重复下载，首屏优先和邻近加载减少了无关图片竞争。此处“再次读取”是后台服务缓存检查，浏览器自身HTTP缓存还可另行复用。

9项实际Chromium检查通过：四张首屏封面真实解码与显示、位图颜色变化、远处图片未提前请求、滚动接近后加载、销毁释放、窗口保持隐藏、零渲染错误。相关单元17项通过，包含别名、瞬时错误、请求合并、单消费者取消、字节逐出及DOM重建释放。

源站不可达、地区网络、ECH握手及临时限速仍会影响首次加载。没有引入代理解锁、持续后台全量预取或无界磁盘缓存。
