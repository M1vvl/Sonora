# 0.3.9 观看历史链路修复

## 定位证据

2026-10-29 只读检查 `%APPDATA%/Agent Pulse/anime/anime-state.json`：已有两条真实观看记录，进度约 30.78 秒与 43.36 秒，并有总时长、来源、剧集地址和更新时间。没有删除、改写或补造这些用户记录。

因此本次可确认的问题是“保存后的历史未通知已缓存的主页”。0.3.8 的内嵌播放器通过独立回调更新后端文件；底层番剧页面仍保留原 DOM 与内存状态，桥接层没有广播历史变化，主页的 `state.history` 可停留在播放前的空数组。仅刷新服务器保存代码不能解决这一显示问题。

## Kazumi 源码对应

分析用户提供的 Windows 2.4.2 源码：

- `lib/repositories/history_repository.dart` 的 `IHistoryRepository.changes` / `HistoryRepository.changes`：历史仓库统一管理写入，Hive 的 `watch()` 将写入、删除和清空变更发送给界面。
- `lib/services/player/history_playback_service.dart`：历史卡片本身不复制查源逻辑，而是通过统一服务恢复条目、原规则、线路和剧集信息。

本任务已有完整源码，采用正常源码检索获取语义；没有将普通源码阅读称为本次新增的二进制 REA Evidence。保留原先 Windows 定向 REA 记录，不修改 Kazumi 原程序或配置。

## 适配实现

- 新增 `src/anime/history.cjs`，统一拥有实际进度保存、清空、历史快照和通知。
- `historyRevision` 作为持久化递增版本；已有记录缺少该字段时按 0 读取，保留原列表。`bootstrap`、`home`、`history` 及变更事件都返回同一 `{history, revision}` 结构，便于界面拒绝较早的异步结果。
- 文件成功写入并原子替换后，才发送 `pulse:anime-history-update`。图像与用量快照不参加此消息；历史上限仍为 100 条。
- 历史 mutation、持久化和通知共用串行队列，避免两个标题同时更新时通知乱序；其他设置保存也在执行时序列化最新状态，防止旧设置快照覆盖刚保存的历史。
- 持久化失败会恢复旧历史和版本，不通知“已保存”；进度小于 1 秒或非有限数值不能创建观看记录。
- 直接打开另一部番剧前先保存旧片进度；关闭时使等待中的打开意图失效，避免返回后出现迟到的重新打开。
- 按新增要求删除桥接层 `openKazumi` 功能及启动外部 Kazumi 的代码。主页历史继续走本应用的统一恢复服务。

## 验证

`tests/anime-history.test.cjs` 新增三项生产边界测试：

1. 实际 `installAnimeBridge` IPC 路由 → 实际番剧服务 → 播放器进度回调 → 实际临时文件 → 通知；断言通知时文件已包含同一进度/版本，重建服务后恢复记录和续播进度。播放器宿主在该测试中使用注入替身，不据此声称完成原生渲染测试。
2. 同时保存两部番剧和网络设置，断言两条历史都保留、版本与通知按 1/2 顺序，清空后为版本 3。
3. 未播放的进度及文件写入失败不会发布虚假历史，失败不损坏原文件。

与既有番剧核心和播放器进度测试合计 18 项通过。实际内嵌播放、主页刷新和打包成品的整合检查由主发布流程继续执行；本文件不将未执行的图形界面操作写成通过。
