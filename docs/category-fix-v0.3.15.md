# 0.3.15 分类目录修复

## 根因与处理

1. Kazumi 镜像的 popular 分类仅覆盖部分标签。实际请求“科幻、冒险、运动、音乐”返回 `data: []`，不能据此把 Bangumi 全库的相同分类当成空白。现在镜像分类首页为空或失败时，改查 Bangumi 官方 `/v0/search/subjects` 的**同一标签**，继续沿用官方返回的原始游标；不会用不相关的热门条目填充。镜像本身正常的分类仍继续使用镜像。
2. LibreTV 复用的豆瓣旧推荐接口对部分标签只返回很少的陈旧推荐，有时返回空数组；旧实现把空数组当成已加载完毕。电视剧还错误发送了 `type=tv&tag=电视剧`，应是 `type=tv&tag=热门`。
3. CMS 的 UI 分类名与实际类别不同。例如“电视剧”在默认源中叫“连续剧”，“纪录片”有的叫“记录片”；电影/连续剧父节点未必聚合子节点。实测如意 `t=2` 不返回列表，`t=1` 仅有一个父节点条目，而其国产剧、动作片等子节点有完整分页。

现在具体影视类别优先查询 CMS 的完整分类目录。`src/movies/categories.cjs` 统一解析别名和分类树，只取对应叶节点并排除伦理、成人、预告、解说分支。跨叶节点按轮转顺序分页，各子类有自己的真实页码、页数和耗尽状态；总目录不能因为一个子类结束而提前停止。空父类别不会再被当成完整目录。源不提供该类别时，才采用正确标签的元数据推荐；不把“热门”伪装成用户选择的类别。

来源编辑/启停后清除对应分类路由和树缓存。分类查询受既有四并发池、单源任务限时、取消与缓存上限约束，没有新增后台轮询。元数据与 CMS 的分页来源一旦选定保持一致，后续页耗尽不会重新混入另一套起点。

## 实测

2026-10-30，在独立临时配置中调用产品目录模块进行真实网络检查；未更改用户偏好。证据：`artifacts/v0.3.15-categories/category-network.json`，探测脚本同目录。Node 网络使用当前环境代理，官方 Bangumi 使用随包 ECH 组件；结果不是合成数据，也不等同于每条影片都已完成播放验证。
